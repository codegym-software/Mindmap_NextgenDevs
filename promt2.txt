Giai đoạn 0 – Chuẩn hoá model & debug interface

Mục tiêu: có cấu trúc dữ liệu rõ ràng cho quyền, log/debug dễ, không “nhớ bằng miệng”.

0.1. Chuẩn JSON Firestore: mindmapAccess/{mindmapId}

Đề xuất format (có thể cắt bớt nếu chưa cần hết):

// Firestore: collection mindmapAccess, document id = mindmapId
{
  mindmapId: string;       // trùng với id của mindmap
  ownerId: string;         // user.id hoặc user.sub

  // (tuỳ chọn) mirror từ Mongo cho debug nhanh
  allowedUsers?: string[]; // userId đã có quyền (VIEW/EDIT)

  pendingRequests: {
    uid: string;
    displayName: string;
    requestedPermission: 'VIEWER' | 'EDITOR'; // NEW
    from: 'direct-link' | 'upgrade-request';  // NEW: vào từ link hay xin nâng quyền
    timestamp: number; // millis
  }[];

  // Lưu quyết định gần nhất cho từng user để trả về "bị từ chối"
  lastDecisions?: {
    [uid: string]: {
      status: 'approved' | 'rejected';
      permission: 'VIEWER' | 'EDITOR';
      decidedAt: number;
    };
  };

  updatedAt: number;
  version: number; // tăng +1 mỗi lần update, dễ debug conflict
}


Cái này giúp bạn mở Firestore console lên là nhìn ngay được:

Ai là owner.

Ai đang pending, xin VIEW hay EDIT.

Ai đã từng bị reject.

0.2. Chuẩn JSON Mongo: collaborators

Hiện bạn đã có collection collaborators. Đề xuất mở rộng:

{
  _id: string;
  mindmapId: string;
  userId: string;

  // Quyền hiện tại
  permission: 'OWNER' | 'EDITOR' | 'VIEWER';

  // Trạng thái lifecycle
  status: 'ACTIVE' | 'PENDING' | 'REJECTED';

  // Nếu là request access / upgrade
  requestedPermission?: 'VIEWER' | 'EDITOR'; // B xin quyền gì
  requestedAt?: Date;

  // Ai tạo / ai mời
  invitedBy?: string;    // ownerId hoặc người mời
  inviteType?: 'OWNER_INVITE' | 'REQUEST_ACCESS' | 'LINK';

  // Nếu owner đã quyết định
  decidedBy?: string;    // userId của owner
  decidedAt?: Date;

  createdAt: Date;
  updatedAt: Date;
}


Nhờ vậy:

BE query được list pending bằng mindmapId + status:PENDING.

Dễ audit: ai xin, xin quyền gì, ai duyệt, lúc nào.

Giai đoạn 1 – Cho B auto “unlock” sau khi được duyệt (ưu tiên của bạn)

Mục tiêu:

B đang bị chặn (403) → thấy màn “Request access”.

A approve → B tự động vào được mindmap, không cần F5.

Chưa cần UI chọn VIEW/EDITOR trong modal, chỉ cần cấp VIEWER là đủ test luồng.

1.1. FE: xử lý lại state ở Editor

a/ Thêm phân biệt 2 nguồn:

backendAccess (từ API GET):

'unknown' | 'allowed' | 'denied'

permission (từ Firestore hook useMindmapAccess):

'loading' | 'allowed' | 'denied'

Editor render theo:

Nếu isDataLoaded === false → spinner.

Nếu backendAccess === 'denied' && permission === 'denied' → AccessDeniedScreen.

Nếu backendAccess === 'denied' && permission === 'allowed' → thử load lại từ BE.

b/ Auto reload khi Firestore báo allowed

Trong Editor:

useEffect(() => {
  if (!id) return;
  if (permission !== 'allowed') return;
  if (!accessDenied) return; // chỉ reload khi trước đó bị chặn

  (async () => {
    try {
      const data = await mindmapsApi.get(id);
      // nếu 200 → hydrate lại store
      setAccessDenied(false);
      setIsDataLoaded(true);

      // TODO: tái sử dụng logic loadData:
      setName(data.name);
      setOwnerId(data.ownerId);
      setGraph(data.nodes, data.edges);
      setGlobalStore(...);
      setBackgroundColor(...);
      setSelectedNodeIds(['root']);
    } catch (e: any) {
      // nếu vẫn 403 thì thôi, giữ nguyên AccessDeniedScreen
      // có thể show toast: "Quyền đang cập nhật, thử lại sau"
    }
  })();
}, [permission, accessDenied, id]);


c/ Sửa init useMindmapAccess

Hiện hook khi không có doc thì set permission = 'allowed'.
Để an toàn hơn:

Nếu !docSnap.exists() → nên set permission = 'denied' (hoặc 'loading') cho tới khi BE confirm.
Đặc biệt với doc private, việc “auto allowed” là nguy hiểm.

1.2. BE + FE: A approve thì cập nhật quyền thật

Tối thiểu để auto unlock chạy được:

Khi A ấn “Duyệt” trong AccessRequestModal, FE phải:

Gọi API cấp quyền thật.

Cập nhật Firestore để B nhận signal.

FE (pseudo):

const handleApproveRequest = async (uid: string) => {
  if (!id) return;
  try {
    // 1. Cấp quyền Viewer trên BE
    await mindmapsApi.updateCollaboratorPermission(id, uid, 'VIEWER');

    // 2. Xoá khỏi pendingRequests Firestore
    await approveRequest(uid);

    addToast('Đã duyệt yêu cầu truy cập', 'success');
  } catch (e) {
    addToast('Không thể duyệt yêu cầu', 'error');
  }
};


BE phía PUT /api/mindmaps/{id}/collaborators/{userId}:

Đảm bảo khi collaborator có permission != null và status=ACTIVE → GET /api/mindmaps/{id} trả 200 cho user đó.

Như vậy:

A ấn “Duyệt” → BE gán VIEWER.

A cũng update Firestore → B nhận permission='allowed'.

B thấy permission='allowed' && accessDenied === true → gọi lại GET.

GET trả 200 → B load mindmap → xong.

Ở giai đoạn này, UI duyệt chỉ cấp VIEWER mặc định, cho nhanh.

Giai đoạn 2 – Duyệt với chọn VIEW/EDITOR + từ chối rõ ràng

Mục tiêu:

A có UI chọn cấp VIEWER hay EDITOR khi duyệt.

A có thể từ chối, B thấy là “đã bị từ chối”.

BE ghi đầy đủ vào collaborators (PENDING → ACTIVE/REJECTED).

2.1. FE: AccessRequestModal cho chọn role

Trong list pending request:

Với mỗi req, thêm dropdown:

“Cấp quyền: Viewer / Editor”

Nút “Duyệt” gửi role:

onApprove(uid, chosenPermission)


ShareModal hoặc Editor bọc lại:

const handleApproveRequest = async (uid: string, perm: Permission) => {
  if (!id) return;
  await mindmapsApi.updateCollaboratorPermission(id, uid, perm);
  await approveRequest(uid); // Firestore
};

2.2. BE: xử lý lifecycle PENDING → ACTIVE / REJECTED

POST /api/mindmaps/{id}/request-access:

Tạo collaborators với:

status: 'PENDING'

requestedPermission: 'VIEWER'|'EDITOR' (từ FE)

POST /api/mindmaps/{id}/requests/{userId}/approve:

Set status: 'ACTIVE'

Set permission = perm từ request

Ghi decidedBy, decidedAt

POST /api/mindmaps/{id}/requests/{userId}/reject:

Set status: 'REJECTED'

(Tuỳ bạn có xoá record hay giữ để log)

Khi reject:

BE cập nhật collaborators PENDING → REJECTED.

BE (hoặc FE tạm thời) update Firestore lastDecisions[uid].status = 'rejected'.

useMindmapAccess đọc lastDecisions → set requestStatus = 'rejected', hiển thị message: “Yêu cầu của bạn đã bị từ chối”.

Giai đoạn 3 – Link chia sẻ công khai (VIEW/EDIT) + request nâng quyền

Mục tiêu:

Trong Share modal:

Chọn “Bất kỳ ai có link: Xem / Chỉnh sửa”.

B truy cập qua link public:

Nếu chỉ được VIEW → vẫn xem bình thường.

Nếu muốn EDIT → có nút “Yêu cầu quyền chỉnh sửa” → join vào queue giống Google Docs.

3.1. BE: mở rộng accessSettings

Trong collection mindmaps:

accessSettings: {
  isPublic: boolean;
  publicAccessLevel: 'NONE' | 'VIEW' | 'VIEW_EDIT'; // hoặc 'VIEW' | 'EDIT'

  // optional cho workspace/team sau
  workspaceVisibility?: 'PRIVATE' | 'WORKSPACE_VIEW' | 'WORKSPACE_EDIT';
}


Rule GET:

Nếu user là owner hoặc collaborator ACTIVE:

Cho phép theo permission.

Nếu isPublic === true:

Nếu publicAccessLevel cho VIEW:

Cho xem (VIEWER).

Nếu cho EDIT:

Cho EDIT (EDITOR tạm thời), nhưng bạn nên yêu cầu login, không cho ẩn danh sửa.

3.2. FE: ShareModal

Trong block “Chia sẻ công khai”:

Thay switch thành:

<select
  value={shareSettings.publicAccessLevel}
  onChange={(e) => handleUpdatePublicAccess(e.target.value as 'NONE'|'VIEW'|'EDIT')}
>
  <option value="NONE">Tắt (Chỉ người được mời)</option>
  <option value="VIEW">Bất kỳ ai có link: Xem</option>
  <option value="EDIT">Bất kỳ ai có link: Chỉnh sửa</option>
</select>


handleUpdatePublicAccess gọi:

await mindmapsApi.updateShareSettings(mindmapId, {
  isPublic: value !== 'NONE',
  publicAccessLevel: value === 'NONE' ? 'DISABLED' : value === 'VIEW' ? 'VIEW' : 'EDIT',
});

3.3. FE cho người đang VIEW xin lên EDIT (câu hỏi bạn nêu)

Khi B có quyền VIEW (do được mời hoặc do link VIEW) mà:

Ấn nút “Edit” hoặc thực hiện thao tác chỉnh sửa.

Nếu BE trả 403 (không cho EDIT):

Show popup nhỏ:

“Bạn hiện chỉ có quyền xem. Bạn muốn gửi yêu cầu quyền chỉnh sửa không?”

Nếu đồng ý:

Gọi POST /api/mindmaps/{id}/request-access với requestedPermission = 'EDITOR'.

Cập nhật Firestore queue (hoặc nhờ BE).

Owner A sẽ thấy trong queue:

Request B tới từ from: 'upgrade-request'.

requestedPermission: 'EDITOR'.

Tức là bạn có 2 luồng request dùng chung hệ thống:

Không có quyền → xin VIEW/EDIT.

Đang VIEW → xin nâng lên EDIT.

Giai đoạn 4 – Workspace / Team

Mục tiêu:

Nếu sau này có workspace (team), chia quyền theo team cho gọn.

4.1. BE: bổ sung layer workspace

users có workspaceId.

mindmaps có workspaceId.

accessSettings.workspaceVisibility:

PRIVATE – chỉ owner + collaborators.

WORKSPACE_VIEW – tất cả trong workspace VIEW được.

WORKSPACE_EDIT – tất cả trong workspace EDIT được.

Khi GET:

Nếu user cùng workspaceId:

Và visibility là WORKSPACE_VIEW/EDIT → auto coi như collaborator với role tương ứng (trừ khi bị explicit block trong future).

4.2. FE: ShareModal

Thêm block nhỏ:

<select
  value={workspaceVisibility}
  onChange={...}
>
  <option value="PRIVATE">Chỉ mình tôi và người được mời</option>
  <option value="WORKSPACE_VIEW">Mọi người trong Workspace: Xem</option>
  <option value="WORKSPACE_EDIT">Mọi người trong Workspace: Chỉnh sửa</option>
</select>

Giai đoạn 5 – Email / In-app notification

Mục tiêu: nâng cấp lên “Google-level experience” nhưng làm sau cho đỡ overload.

Ý tưởng:

Khi có REQUEST_ACCESS:

BE push:

1 record vào notifications collection (Mongo).

(Sau này) trigger gửi email nếu owner bật.

FE:

Nút “Chuông” trên toolbar không chỉ đọc từ Firestore mà còn có thể đọc từ API /api/notifications.

Bạn có thể để phase này sau khi core flow request/approve/deny đã chạy cực ổn.
