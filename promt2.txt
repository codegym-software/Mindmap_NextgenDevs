Giai đoạn 6: Tối ưu hóa Luồng Dữ liệu FE (Loại bỏ Map trung gian)
Mục tiêu: Dọn dẹp code FE để loại bỏ vòng lặp List -> Map -> List không cần thiết. Đảm bảo toàn bộ luồng save (lưu trữ) của FE sử dụng List (Array) nhất quán.

Việc cần làm:

Cập nhật src/pages/Editor.tsx: Sửa useEffect[auto-save] (logic handleSave và saveGuestDoc) để gửi thẳng nodes (dạng List) từ useEditorStore.

Cập nhật src/services/mindmapsApi.ts: Sửa hàm update để chấp nhận nodes (dạng List) và loại bỏ logic Object.values().

Kết quả: Luồng dữ liệu được tối ưu thành List (Zustand) -> List (API Layer) -> List (BE). Code sạch hơn, nhanh hơn và sẵn sàng cho các giai đoạn tiếp theo.

Giai đoạn 7: Tách biệt Undo/Redo (0.5s) và Lưu trữ (5s)
Mục tiêu: Triển khai logic 2 tốc độ: Undo/Redo (RAM) phải nhanh (0.5s), Lưu trữ (DB/LocalStorage) có thể chậm hơn (5s).

Việc cần làm (Toàn bộ ở src/pages/Editor.tsx):

Import useDebouncedCallback (từ use-debounce).

Xóa pushHistory ra khỏi tất cả các hàm hành động (handleAddChild, handleDeleteNode, handleDragEnd, stopEditing, handleUpdateNode, v.v.).

Tạo 2 hàm debounced mới:

debouncedPushHistory (delay 0.5s): Chỉ gọi pushHistory(get().nodes, get().edges).

debouncedPersistData (delay 5s): Gọi logic useEffect[auto-save] cũ (tức là mindmapsApi.update hoặc saveGuestDoc).

Sửa tất cả các hàm hành động: Sau khi gọi setGraph(...), chúng sẽ gọi cả debouncedPushHistory() và debouncedPersistData().

Kết quả: Undo/Redo được cá nhân hóa 100% và tách biệt hoàn toàn khỏi logic lưu vào DB. Trải nghiệm người dùng mượt mà hơn.

Giai đoạn 8: Nâng cấp Backend WebSocket để Xử lý "Bản vá" (Patches)
Mục tiêu: "Dạy" cho MindmapUpdateHandler.java cách nhận diện và broadcast các thay đổi (patch) cụ thể, thay vì chỉ là một "phòng chat" chung chung.

Việc cần làm:

Tạo DTOs (Java): Tạo các file record mới trong features/websocket/dto/ (ví dụ: NodeMovePatch.java, NodeTextPatch.java, NodeCreatePatch.java... để định nghĩa cấu trúc {"type": "...", "payload": {...}}).

Cập nhật MindmapUpdateHandler.java:

Sửa handleTextMessage(String message): Dùng Jackson (ObjectMapper) để deserialize message thành một BasePatch (DTO cha).

Dùng switch(basePatch.getType()) để xác định loại patch (ví dụ: NODE_MOVE).

Quan trọng: Giữ nguyên logic "pure broadcast". Handler này chỉ broadcast bản vá cho người khác, nó không lưu vào DB (việc đó vẫn do HTTP PUT 5s đảm nhiệm).

Kết quả: Backend WebSocket trở thành một bộ định tuyến (router) "bản vá" thông minh, sẵn sàng cho Giai đoạn 9.

Giai đoạn 9: Tích hợp Frontend WebSocket (Gửi và Nhận "Bản vá")
Mục tiêu: Hoàn thiện vòng lặp cộng tác. FE phải gửi patch khi thay đổi và nhận patch từ người khác.

Việc cần làm (Chủ yếu ở src/pages/Editor.tsx):

Gửi Patch: Sửa tất cả các hàm hành động (handleDragEnd, stopEditing, v.v.): Ngay sau khi setGraph, gọi ws.send(...) ngay lập tức với patch JSON tương ứng (ví dụ: {"type": "NODE_TEXT_CHANGE", ...}).

Kết nối WS: Thêm useEffect để khởi tạo kết nối WebSocket (sử dụng accessToken từ useAuth để xác thực qua WebSocketAuthInterceptor.java).

Nhận Patch: Triển khai logic ws.onmessage:

Parse JSON nhận được.

Dùng switch(message.type) để xử lý.

Ví dụ: case "NODE_MOVE": Lấy nodes hiện tại, tìm node theo id, cập nhật x, y, và gọi setGraph(newNodes, edges) (nhưng không gọi pushHistory).

Kết quả: Ứng dụng có tính năng cộng tác real-time. User A thay đổi, User B thấy ngay lập tức. Undo/Redo của User A không ảnh hưởng đến User B.
